# RecreatePro: dedicated reference-to-production app

## Owner request
A source image (including one side of a van) can seed reconstruction of a complete wrap. Choose a path first, upload, prompt requested edits, then review and produce. The transfer-to-another-vehicle path is also available. RecreatePro is its own app on OS.DesignProAI, not hidden inside the legacy ProductionFlow prep page. Deploy using Git.

## Implementation
- `/recreatepro`: a dedicated public intake, with authenticated submission and owner-scoped saved-job reads. Sidebar and tool registry entry; `/productionflow?tab=prep` and the VehiclePro reference handoff resolve here. Generation-specific ProductionFlow URLs stay untouched.
- Three task choices: exact reconstruction, completion of missing surfaces, transfer to another vehicle. Supplied surfaces can be tagged. JPG/PNG/WebP and PDF page 1 references; the original PDF is retained as an uploaded attachment. Six references maximum, 25 MB each.
- Reuses WallPro's actual equal-card primitives and existing blue design language. Real uploads, panels and previews replace placeholders as they arrive. No fabricated processing percentages, test images presented as customer outputs, or automatic success claims.
- Uploads use `dpApi.uploadRevisionAsset` with the same reserved Generation ID used in the v3 request. Raw edit text remains verbatim in `brief`; bounded path instructions use the existing `styleDescriptors` contract.
- Existing `design-panel-ai-generate` exact-reference branches now consume only tagged RecreatePro task guidance. Non-RecreatePro requests are unchanged. The mechanically generated shared assembly is regenerated. The proof-head validator accepts the real reproduction specialist only with this tagged task; arbitrary identities remain rejected.
- The same request, immutable proofs, handoff, RevisionStudioIQ, revision-pinned purchase and manufacturing chain as VehiclePro. No second renderer, panel producer, payment endpoint, production approval or delivery pipeline.
- Browser drafts are account-scoped and expire after 24 hours. The exact submitted request is saved before POST and reused on an ambiguous retry. A durable request URL resumes reads; it never resubmits generation on mount.
- Existing subscribers and one-time Production Pack buyers use the same server-authorized generation/purchase rules. No client-side overage charge or synthetic entitlement is introduced. Pack pricing and billing policy are unchanged.
- Transfer after review uses this version's real saved panel bytes and verifies their hashes. It creates a new generation; it does not alter the original job or infer a new design from the old screenshot again.

## Billing limitation identified during review
The current repository's pricing page links to a `/checkout` route that is not served. The production Supabase `create-checkout` function was not found. This rebuild does not invent new Stripe subscription products or claim that new subscription enrollment is working. Existing subscriptions can be used; final Production Packs use the existing one-time gateway checkout. New subscription enrollment requires a separately verified billing repair before marketing that enrollment path.

## Verification and release requirements
Run scoped input, reference-guidance, shared-assembly, proof-head, routing and naming checks; semantic checks for the changed app entry; real React/Chromium UI cases with mocked auth/API; and the full application build. UI fixtures are not AI-generation acceptance evidence.

Deploy only an exact Git release via existing release/deploy workflows. All design-routing toggles remain unchanged. The edge rollout must include `production-panel-proof` and `design-panel-ai-generate` because they consume the shared assembly. Read the deployed source identities back. A real one-sided source -> completed proof set -> revision -> approved paid production -> downloaded panels remains the live acceptance criterion. No code or UI test substitutes for inspecting exported artwork.
